# RIVET 电动自行车管理员后台 V2：架构审查与改造计划

审查日期：2026-10-13  
审查范围：商城根应用、`admin-app/`、Prisma schema 与迁移、PostgreSQL 当前数据、购物车/结账、PayPal 沙盒、图片存储、测试与运行配置。

## 一、结论摘要

现有项目已经具备可运行的本地电商闭环：英文美国商城、独立中文后台、商品多图与多规格、库存检查、待付款订单、PayPal 沙盒创建/回跳/Webhook，以及询盘管理。现阶段适合继续增量升级，不应推倒重建。

但当前后台仍是“小型运营控制页”，不是可支撑多市场、多角色、库存追踪和订单履约的管理平台。主要瓶颈位于领域模型和服务边界，而不是视觉样式。正确顺序是：先把订单/库存/权限等平台基础拆开，再扩展商品域和美国/欧洲市场，最后接入履约、客户、营销和内容模块。

## 二、当前真实状态

### 应用边界

- 商城：仓库根目录 Next.js 应用，默认 `http://localhost:3000`，英文、美国市场。
- 管理后台：`admin-app/` Next.js 应用，默认 `http://localhost:3001`，默认中文。
- 两个应用共享同一 PostgreSQL、同一 Prisma schema、同一仓库依赖和根环境变量。
- 商城不存在 `/admin` 路由，应用入口已经分离；但尚不是完全独立仓库或完全隔离部署。
- 商品图片当前通过本地持久化目录和商城图片 API 提供；跨机器部署前必须切换到共享存储或对象存储。

### 当前数据库快照

|---|---:|
| 商品 | 3 |
| 市场版本 | 3 个，全部为 US |
| 规格/SKU | 6 |
| 账面库存 | 42 |

说明：审查只读取数据，没有修改订单或释放库存。当前 1 件预留库存来自待付款订单，现有代码没有超时/取消后的统一释放机制。

### 已有可保留能力

- 商品草稿、上架、下架和重新上架。
- 商品多图上传、主图选择和规格管理。
- 后台保存后，商城刷新直接读取 PostgreSQL 新数据。
- 结账服务端重新校验商品状态、规格、价格和库存。
- Serializable 事务内预留库存。
- PayPal 浏览器回跳不直接认定付款成功；只有验证通过的 Webhook 标记已付款。
- PayPal 事件 ID 唯一约束，具备基础幂等保护。

## 三、最优先的 3 个架构问题

### P0-1：订单、支付、履约共用一个状态字段

`Order.status` 同时容纳待付款、PayPal 已批准、已付款、已取消、已履约和已退款。管理员页面也直接编辑这个字段。这会导致：

- 付款、取消、发货和退款之间缺少合法转换规则。
- 管理员取消订单时不会自动释放预留库存。
- “已退款”没有退款金额、PayPal 退款 ID、原因或时间记录。
- “已履约”没有包裹、承运商、追踪号或发货记录。
- Webhook 与人工操作可能竞争更新同一状态。

目标模型应至少拆为：

- `Order.businessStatus`：DRAFT/PENDING/CONFIRMED/CANCELLED/CLOSED。
- `Payment.status`：PENDING/AUTHORIZED/CAPTURED/FAILED/PARTIALLY_REFUNDED/REFUNDED。
- `Fulfillment.status`：UNFULFILLED/PARTIAL/FULFILLED/RETURNED。
- `Refund`、`Shipment`、`OrderTimelineEvent` 保存事实记录，而不是只覆盖最终状态。

### P0-2：库存只有余额，没有可追溯账本和预留生命周期

当前每个变体只有一行 `onHand/reserved`。结账增加预留，付款 Webhook 扣减余额并减少预留；但是支付失败、订单取消、超时、库存调整、退货入库和多库位都没有记录。

目标模型应包括：

- `InventoryLocation`：仓库/库位。
- `InventoryBalance`：按 `variant + location` 保存当前汇总。
- `InventoryMovement`：入库、出库、调整、退货等不可变流水。
- `InventoryReservation`：订单级预留、到期时间、释放原因和状态。
- 所有库存变化必须在事务内同时写余额与流水，并带操作者或系统来源。

### P0-3：商品与市场模型过度固定，无法自然扩展欧洲和配件

`MarketVersion` 固定包含电机、速度、续航，`Variant` 固定包含颜色、电池、电机、轮胎。该结构可以管理当前三款美国电动自行车，但无法优雅支持配件、任意选项、市场级 SKU 发布与不同币种价格。

目标模型应拆为：

- `Category`、`Product`、`ProductMedia`、`ProductSpecification`。
- `ProductOption`、`ProductOptionValue`、`Variant`、`VariantOptionValue`。
- `Market`、`ProductListing`、`VariantPrice`，分别管理可见性、文案和 USD/EUR 价格。
- `ProductCompatibility` 管理配件与车型/规格兼容关系。
- 物理 `Variant` 与市场价格分离，才能让美国和欧洲共享一个 SKU 库存或按业务规则分别管理。

## 四、其他重要问题

### 权限与审计

- 账号来自 `ADMIN_EMAIL/ADMIN_PASSWORD` 环境变量。
- JWT 固定写入 `admin` 角色。
- 没有管理员用户、密码哈希、角色、权限、会话撤销、登录记录或 AuditLog。
- 所有 Server Action 只有“是否管理员”的二元判断，无法控制商品、订单、退款和权限管理等高风险操作。

### 管理端结构

- 商品、库存、订单、询盘全部堆叠在一个约 139 行的页面中。
- 所有写操作集中在一个约 315 行的 `actions.ts`。
- 没有模块级路由、列表查询服务、分页、搜索、筛选、详情页或领域服务。
- 后台统计只取最近 20 个订单，收入仅按这批记录和单一状态计算，不可作为真实运营报表。

### 可靠性与数据一致性

- 商品数据库查询异常会静默返回演示商品，可能掩盖生产故障。
- PayPal Webhook 在数据库事务内发送邮件；邮件网络失败可能回滚支付入账和库存扣减。
- 订单号仅基于毫秒时间，没有数据库序列或冲突重试策略。
- 商品和规格硬删除依赖局部检查，未来应统一为归档/停用和审计策略。

### 多市场缺口

- 前台、购物车、校验、结账、运费、地址、货币格式均固定为 US/USD。
- 数据库虽然已有 EU 枚举，但实时数据库没有 EU 数据。
- 没有欧洲地址、VAT/税费、配送区、法规文案、市场发布和 EUR 价格工作流。

### 测试缺口

- 当前自动测试仅覆盖美国购物车校验和固定运费计算。
- 缺少数据库集成测试、管理端 Action 测试、权限测试、库存并发/补偿测试、订单状态机测试、PayPal Webhook 重放测试和双应用端到端测试。

## 五、建议目标架构

### 目录与模块边界

保留两个 Next.js 应用，但把共享业务代码逐步收敛到仓库内公共模块，而不是继续让页面直接操作 Prisma：

```text
storefront (root)
  -> storefront use-cases
admin-app
  -> admin use-cases + permission checks
shared domain/application layer
  -> catalog / inventory / orders / payments / fulfillment / identity / audit
shared Prisma repository layer
  -> PostgreSQL
external adapters
  -> PayPal / mail / media storage
```

第一阶段可先在现仓库内建立 `src/server` 或共享包边界，不要求立即拆成多仓库。商城和后台仍各自部署、各自路由，但复用同一领域规则。

### 后台信息架构

建议中文后台路由：

- `/dashboard`：待处理订单、低库存、支付异常、近期销售。
- `/products`、`/products/[id]`：列表、详情、市场、媒体、规格、变体。
- `/inventory`：库存余额、流水、预留和调整。
- `/orders`、`/orders/[id]`：业务状态、支付、履约、时间线。
- `/customers`：客户与地址。
- `/inquiries`：询盘。
- `/discounts`：折扣规则。
- `/content`：CMS 内容。
- `/settings/markets`、`/settings/users`、`/settings/audit`。

### 数据原则

- 金额继续使用最小货币单位整数，并明确 `currency`。
- 订单行保留商品、SKU、选项、单价等下单快照。
- 支付和库存流水采用追加事实记录，不用覆盖式字段代替历史。
- 所有后台写操作记录管理员、动作、对象、前后差异和时间。
- 产品发布与变体启用分开；市场可见性与物理 SKU 分开。

## 六、分阶段行动计划

### Phase 0：审查与边界确认（当前）

1. 确认商城市场形态、RBAC 上线深度和欧洲优先级。
2. 确认现有 1 个待付款订单/1 件预留是否是测试记录，并决定后续如何处理。
3. 冻结目标数据契约和迁移顺序。

验收：本审查文档获确认，关键歧义消除，不执行破坏性迁移。

### Phase 1：后台 UI 与平台基础

1. 建立中文后台壳层、侧边导航、面包屑、响应式布局和统一反馈。
2. 拆分 Dashboard、商品、库存、订单、询盘模块路由。
3. 建立可复用表格、分页、搜索、筛选、空状态、错误状态和危险操作确认。
4. 引入 `AdminUser/Role/Permission/AdminSession/AuditLog`；若用户选择渐进方案，先兼容现有环境变量管理员完成首账号引导。
5. 建立领域服务边界，页面与 Action 不再直接散落业务规则。
6. 增加权限、审计和关键管理操作集成测试。

验收：后台默认中文；所有入口真实可用；没有死按钮；旧商品、订单、询盘仍可读取；商城、购物车、下单和 PayPal 沙盒不回归。

### Phase 2：商品域与多市场基础

1. 新增 Category、ProductMedia、ProductSpecification、Option/Value、Variant 组合与 Compatibility。
2. 新增 Market、ProductListing、VariantPrice，支持 USD/EUR 和市场级发布。
3. 通过兼容字段和回填脚本迁移现有 3 个商品、6 个 SKU，不直接删除旧列。
4. 后台实现商品列表/详情、媒体排序、分类、参数、选项组合、变体、美国/欧洲定价和发布检查。
5. 商城先通过兼容读取层继续消费美国数据；欧洲前台是否同期启用由用户确认。
6. 把数据库故障与“明确演示模式”分开，禁止静默展示夹具冒充真实商品。

验收：现有商品无损迁移；美国商城行为不变；后台能完整维护目标商品域；市场价格和发布状态有自动测试。

### Phase 3：库存与订单核心

1. 上线库位、余额、流水和订单预留实体。
2. 为现有余额创建迁移基线流水。
3. 拆分订单业务/支付/履约状态并实现合法状态机。
4. 增加预留过期、取消释放、付款扣减、退款/退货补偿。
5. 将邮件从 PayPal 数据库事务中移出，采用 Outbox/任务重试。

### Phase 4：欧洲商城与运营模块

1. EU/EUR 前台、地址、配送区、税费和合规文案。
2. 客户、折扣、售后、CMS 和运营分析。
3. 生产迁移演练、备份/回滚、灰度发布和监控。

## 七、迁移策略

1. 所有 schema 变更采用新增表/新增可空字段优先。
2. 先部署双写或兼容读取，再回填旧数据，再切换读取路径。
3. 验证行数、金额、SKU、库存余额和订单快照后，才讨论删除旧字段。
4. 旧字段删除、真实订单修复、库存冲销、生产迁移均需用户单独确认。
5. 每个阶段必须通过 Prisma validate、迁移测试、TypeScript、Lint、单元/集成测试、双应用构建和端到端回归。

## 八、需要确认的三个决策

1. 美国和欧洲最终是同一个商城内切换市场/币种，还是两个独立前台站点？当前只有“美国商城 + 中文后台”两个网站，并没有欧洲商城。
2. Phase 1 是否立即做真正的多管理员 RBAC，还是先保留当前单管理员登录，同时落数据库账号、审计和未来权限扩展基础？
3. Phase 2 是否要求欧洲商城同步上线，还是只先完成多市场数据模型和后台 EUR 管理，美国商城保持现状，欧洲前台放到 Phase 4？

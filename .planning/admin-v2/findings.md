# 后台 V2 审查发现与决策

## 已知基线
- 商城和管理后台是两个独立 Next.js 应用，默认分别运行于 3000 和 3001。
- 两个应用共享 PostgreSQL；当前商品编辑、图片、多规格、库存和上下架流程已完成并验证。
- 当前运行目标仍包括完整保留购物车、下单、后台和 PayPal 沙盒。

## 待验证
- 现有商品、库存、订单、支付与管理员模型是否足以支撑美国和欧洲市场。
- 订单业务状态、支付状态、履约状态是否存在混用。
- 库存是否具备库位、流水、预留、释放与可追溯能力。
- 商品域是否具备分类、媒体排序、选项组合、市场定价、技术参数和配件兼容关系。
- 当前单管理员认证如何演进为 RBAC 和审计，而不破坏本地运行体验。

## 待用户确认
- 美国/欧洲是两个独立商城前台，还是一个商城内切换市场和币种。
- Phase 1 是否立即落地多管理员 RBAC，还是先保留单管理员并建立可迁移基础。
- Phase 2 是否必须同时上线欧洲市场，还是先把数据模型做成多市场、界面仍优先美国。

## 仓库与数据模型初审
- 仓库已实际拆成根目录商城和 `admin-app/` 管理端；两端共享根目录 Prisma schema 与依赖安装，不是两个完全独立部署仓库。
- 当前工作树包含上一阶段尚未提交的后台拆分和商品管理成果；本次审查必须在其上增量工作，不能回滚或覆盖。
- `MarketCode` 已有 `US`、`EU`，但 `MarketVersion` 仍把电机、速度、续航等自行车字段固定在市场版本上，无法自然支持通用配件和可扩展技术参数。
- `Variant` 直接承载颜色、电池、电机、轮胎等固定字段；没有产品选项/选项值/组合模型，也没有市场级变体价格模型。
- `Inventory` 只有每变体一行 `onHand/reserved`，没有库位、库存流水、原因、操作者、订单预留记录或释放记录。
- `Order.status` 单字段同时包含 `PENDING/APPROVED/PAID/CANCELLED/FULFILLED/REFUNDED`，已经把业务、支付和履约生命周期混在一个状态机中。
- 尚无 Category、Customer、Address、AdminUser、Role、Permission、AuditLog、Location、InventoryMovement、Shipment、Refund、Discount、CMS 等核心模型。
- 根包大量使用 `latest` 版本，而管理端锁定 Next.js 16.3.4，长期存在依赖漂移和双应用版本不一致风险。

## 关键业务链路初审
- 管理端当前是一个超长单页：商品、库存、订单和询盘全部在 `admin-app/src/app/page.tsx` 中直接查询并渲染，缺少模块路由、列表/详情分离、服务层和权限边界。
- 管理员账号来自环境变量，JWT 中固定写入 `role: admin`；数据库没有管理员、角色、权限、会话或审计记录，因此无法支持多人协作和责任追踪。
- 商城 `getProducts()` 只查询美国市场；数据库异常时会静默退回演示商品，这会把真实数据故障伪装成正常商城内容，后台与前台也可能出现不一致。
- 结账会在 Serializable 事务中增加 `Inventory.reserved`，但订单取消、PayPal 失败/超时、管理员取消时没有统一释放预留库存的流程。
- PayPal 回跳成功只把同一 `Order.status` 改为 `APPROVED`，Webhook 再改为 `PAID` 并扣减库存；该设计虽保护了 Webhook 确认边界，但支付、业务、履约三类状态相互覆盖。
- 管理员能把订单同一状态字段改为取消、履约、退款等，但除了禁止手动设为 PAID 外，没有状态转换规则、库存补偿、退款凭证、履约记录或审计日志。
- PayPal Webhook 在数据库事务内部调用发信，外部网络 I/O 会拉长事务；发信失败还可能导致支付事件和库存扣减一起回滚，需改为事务后可靠任务/Outbox。
- 前台价格、运费和地址校验均为美国固定逻辑；欧元、欧洲税费、地址格式、配送区和市场选择尚未形成完整链路。

## 迁移、测试与运行配置
- 目前只有初始迁移和商品多图迁移；尚无可支撑后台 V2 的渐进兼容迁移或数据回填脚本。
- 种子数据只创建美国市场自行车，且 `upsert.update` 为空；种子不能演示或验证欧洲市场、配件、分类、权限、客户和复杂订单。
- 现有自动测试只有运费计算与美国结账字段校验共 5 个断言，没有覆盖管理端 Action、库存并发/释放、订单状态转换、PayPal Webhook 幂等补偿或数据库集成。
- README 明确当前商品、库存、政策和图片都是开发夹具，项目尚未获准处理真实订单；这与本次升级必须保留的沙盒/本地边界一致。
- 本地上传依赖共享磁盘路径；若商城与后台部署到不同机器，必须先换为对象存储或共享持久卷。
- 根应用与管理应用都读取仓库根环境变量，仍是共享运行配置；“独立网站”当前是独立 Next.js 入口和端口，不等于完全隔离的部署单元。

## 实时数据库快照
- 商品 3 个；MarketVersion 3 个，全部为 US；Variant 6 个。
- Inventory 共 6 行，`onHand` 合计 42，`reserved` 合计 1。
- 订单 1 个，状态为 PENDING；PaymentEvent 0 个；Inquiry 1 个。
- 审查未改动任何真实数据。`reserved = 1` 与待付款订单同时存在，但现有代码没有订单超时或取消后统一释放流程。

## Phase 0 判断
- 现有项目应增量演进，不重建；商品管理成果、双应用入口和 PayPal Webhook 验证边界应保留。
- 最先修复的领域问题依次是：订单状态拆分、库存账本/预留生命周期、可扩展商品与市场模型。
- RBAC/AuditLog 是 Phase 1 的平台基础；欧洲前台是否同步进入 Phase 2 仍需用户确认。
- 完整审查文档：`.planning/admin-v2/architecture-audit.md`。

## 用户确认的目标边界
- 一个商城未来在 US/USD 与 EU/EUR 之间切换，不建设两个独立前台站点。
- 当前继续使用单管理员，但数据库与服务边界要为未来多管理员、RBAC 和审计做好准备。
- 本轮先完成后台对 US/EU 商品、市场发布和价格的管理；欧洲前台暂不开放。
- 为避免同一物理 SKU 在两个市场重复库存，市场价格/发布应从 Variant 物理库存实体分离。

## 后台设计方向
- `design-taste-frontend` 明确将后台和数据表列为适用范围之外，因此不套用营销落地页视觉规则。
- 采用 Shopify 式电商运营信息架构与紧凑、清晰、低装饰的后台模式；沿用现有 Tailwind/CSS，不为了视觉重构引入重型组件库。

## 已冻结的数据兼容策略
- `Variant` 继续保留原 `marketVersionId` 和 `price`，确保美国商城与 PayPal 链路无需同时改写；新增 `productId` 表示物理 SKU 归属。
- `VariantPrice` 按 `variant + market` 保存 USD/EUR 价格和启用状态；Inventory 仍只关联物理 Variant，因此两个市场共享库存。
- `MarketVersion` 继续作为市场发布/文案实体，新增 `published/locale/SEO`；迁移自动创建未发布的 EU 市场版本。
- 美国价格从旧 `Variant.price` 回填并启用；欧洲价格回填为 0 且禁用，避免未经确认的汇率或售价进入运营数据。
- 分类、媒体、技术参数和 Color/Battery/Tire 选项从现有商品字段增量回填，不删除旧字段。
- 单管理员仍由环境变量认证；数据库加入 OWNER 角色、管理员、会话和审计表，为未来切换数据库认证预留路径。
